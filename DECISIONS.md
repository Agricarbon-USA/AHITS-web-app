### D26 · Late-synced daily check carries its ORIGINAL business date (bounded past window; collisions surfaced, never merged)
- **Date:** 2026-07-28 · **Owner:** Max · **Status:** ACTIVE · **Shipped:** CC-29 PR-2 (#203)
- **Decision:** A daily check queued/parked on day N and replayed later is filed under the day it was **performed**, not the sync day. The server trusts the client-stamped `businessDate` only within a bounded **PAST window of 3 days** (`PAST_WINDOW_DAYS=3`); anything older, or **any future date**, is clamped to today (FND-7 preserved — future/pre-dating to dodge the missed-check alert stays blocked). A **past-date** submission that collides with an existing `(vehicle, date, operator)` row returns **409** ("A check for `<date>` already exists for this vehicle.") — the offline queue surfaces it as a terminal `failed`/discard-able item; it is **never a silent upsert-merge** (the day-N-vs-day-N+1 write-loss the review's §1.1 found). Same-day resubmit keeps upsert-update. The daily-check POST wraps in `withIdempotency` (scope `daily-check`) so an exact replay whose 201 ack was lost returns the cached 201 instead of false-failing on the new 409.
- **Rationale:** the P0 charter promise is "zero lost writes"; re-dating a late check both created a false MISSED for day N and silently overwrote day N+1's real check. Trusting a *bounded* past window recovers the true date without reopening the pre-dating hole.

### D27 · Sliding session renewal — refresh past half-life, hard cap 14 days since PIN entry
- **Date:** 2026-07-28 · **Owner:** Max · **Status:** ACTIVE · **Shipped:** CC-29 PR-3 (#205)
- **Decision:** The 24h JWT is re-minted in the proxy on any authenticated request past its half-life, carrying the **same claims** + a fresh 24h exp, so a crew signed in the same morning no longer hits a **synchronized mid-shift expiry**. Bounded by an `authAt` claim (epoch of original PIN entry, carried unchanged through every renewal): once `now − authAt > 14 days` the token is allowed to expire naturally. **Tradeoff (accepted):** fixed 24h bounded a stolen token to ≤24h; sliding renewal lets an *actively-used* stolen token live longer — bounded to ≤14 days since PIN entry, never infinite. **Instant revocation is unaffected** — every API route still runs DB-backed `getSession()` (tokenVersion / isActive / role), so suspend/force-logout kill a renewed token on its next online request. Mint/renew helpers + cookie flags live in one edge-safe `session-edge.ts` (jose-only) shared by `session.ts` and `proxy.ts`.
- **Rationale:** the synchronized JWT cliff (review §1.3a) bounces the whole fleet mid-task on the same schedule; the 14-day cap keeps the security envelope finite.
