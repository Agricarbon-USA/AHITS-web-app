# Airtable (Team/Business/Enterprise Scale, current stack as of 2026-07-31: Interfaces, Forms, Automations, native mobile app + barcode field, Portals add-on, Web API, Omni AI)

## Design

# AHITS-on-Airtable — the honest best design (as of 2026-07-31)

Position statement first, because credibility depends on it: **Airtable's official support docs state "Offline access to Airtable is not supported"** [C13], and the register's hardest MUSTs (R-OFF-1..7) are offline MUSTs. This design does not pretend otherwise. What it does claim: Airtable can genuinely win the admin/reporting layer, the CC-18 week board, the availability calendar, most of the alert engine, and the bus-factor problem — at marginal cost on a plan the company already pays for — and it can carry a *redesigned* capture layer whose viability depends on one empirical question this design flags for a week-1 field spike: **how often is CUL005 signal actually zero vs merely bad, and is a connectivity-required capture layer survivable there?** The corpus's answer ("lie-fi is the norm, the queue needed 12s/20s timeouts") strongly suggests no. I design as if capture must work anyway, and concede where it can't.

## 0. Architecture at a glance

- **One production base: `AHITS Ops`** (~24 tables, below) + **`AHITS Archive`** base (annual roll-off; record caps are per base) + optional **`AHITS Money`** base for invoices/rates if cost-visibility separation wants a harder wall than interface-only access.
- **Operators = billable collaborators with interface-only access** (they see Interfaces, never the raw base — this is how "operators never see cost/spend" is enforced; interface pages simply don't render cost fields) [C22]. They run the **native Airtable mobile app** (iOS 16+ / Android 7.0+ [C27]) — the only path to the barcode-scanning camera flow [C16].
- **Admins (2–5) = full base collaborators** on desktop + mobile.
- **External parties (hubs, shops) = zero-seat**: free read-only share links / read-only portal users (non-billable) [C19] for viewing, plus **public Airtable Forms with `prefill_`/`hide_` URL params** for write-back events [C18].
- **Automations (≤50/base cap [C10])** are the alert/cron/state-transition engine; 15-minute minimum schedule granularity [C12].
- **Omni AI** for admin-side ad-hoc interface/report building — GA on all plans with AI enabled [C25].

### The capture-path fork (decide in week 1)
- **Path A (recommended): operators as collaborator seats on the native app.** Gets: barcode field scanning [C16], interface record-creation forms on mobile [C17], current-user-filtered Today page [C22]. Costs: full per-seat price; requires each contractor to have an email + Airtable account (concedes R-AUTH-1/2).
- **Path B: operators as Portal guests (mobile web).** Gets: ~60–70% cheaper seats [C19][C21], branded sign-in. Loses: the native app entirely — and **the barcode field does not work on mobile browsers** [C16], so Path B has no in-app scanning at all. Portal mobile-app support is not documented [C19]. Path B is priced in the pricing section but **not recommended for capture** — it is the "browser tab" experience the UX review already flagged as the fleet's worst case.

## 1. Schema (the part Airtable does well)

~24 tables in `AHITS Ops`. Linked records + rollups express most of the Prisma model's relational shape; what they cannot express is enforcement (see §8).

| Cluster | Tables |
|---|---|

| Inventory | `InventoryItems` (ItemType: SERIALIZED/CONSUMABLE single-select — R-INV-1's split is two child tables, not a flag), `InventoryUnits` (per-unit serial, QR, status, soft-delete checkbox), `InventoryStock` (per-hub rows: quantity, reservedQty, low-stock threshold, reorder URL, supplier, unit cost) |

Attachment storage is comfortable: register-estimated 1k–10k photos/yr at 0.1–0.3MB ≈ 0.3–3GB/yr against 20GB (Team) / 100GB (Business) per base [C6]. **Caveat that must be engineered around: Airtable attachment URLs expire (≥2h guarantee); any external system consuming photos must download content, never hot-link** [C23].

## 2. Operator phone flow — the daily check, step by step (Path A, native app)

Design principle: Airtable cannot win a 16-tap per-item stepper, so the check is redesigned **exception-first** (product concession Max must sign: blanket attestation + named exceptions, instead of per-item Yes/No/N-A rows; per-item data quality — the thing R-OFF-6 protects — is reduced).

1. Open app → **"My Day" interface page**, filtered to current user ("Viewer's records only") [C22]: my rig, per-vehicle check-done/due status (rollup), transfers waiting on me, awaiting-pickup cards, open requests. This satisfies R-FRIC-3's "a day, not a menu" *in structure* — the D5 gate shape exists in Airtable's vocabulary.
2. Tap **"Start check"** button on the vehicle row → interface record-creation form (supported on mobile app [C17]) with vehicle/operator/date defaulted from context.
3. **"All items OK?"** toggle (default). If not OK → multi-select the failed items from the vehicle-type's template list + required note + photo attachment.
4. Odometer (numeric, 5 keys). Site: single-select of project sites (carry-forward of yesterday's free-text is not natively possible; a select list is the workaround).
5. Submit.

**Honest tap count: ~6–8 taps + 5–10 keys, ~60–90s online on good signal** — misses AHITS's measured 5-tap/35s (R-FRIC-1) but is inside the PRD's 90s ceiling *when the network cooperates*. On lie-fi it does not degrade gracefully: the form needs live connectivity to load and to submit; there is no cached form, no queue, and no bounded-timeout enqueue (R-OFF-2 unmet). A February 2026 community thread reports the mobile app **silently failing to save edits even on Wi-Fi**, with no official response [C15] — I flag it because a champion who hides it loses the room later.

## 3. QR / custody

- Every `Vehicle`/`InventoryUnit` row carries a **barcode field**; associating an existing physical label = open row → scan (camera fills the field) [C16]. Uniqueness-on-associate is an automation check, not a 409 (see §8).
- **Scan-to-record**: the native app's barcode field is a *fill-a-field* mechanic, not a global "scan → open matching record" resolver. The workable pattern: a persistent `ScanActions` table + interface page — operator taps "Scan", scans into a new row's barcode field, an automation matches the code against Vehicles/Units and writes back a link; the operator then opens the matched record from the same page and uses **status-conditional buttons** (interfaces support conditional buttons/sections on mobile [C17]): Available→Check Out (button runs an update-fields automation), Checked Out→Check In / Report Problem, Vehicle→Start Daily Check. That is scan → wait for automation round-trip → tap. **It will not reliably meet ≤500ms and it requires signal; offline scan resolution (R-QR-1's offline clause) is unmet** [C13]. Whether barcode scanning works *inside interface pages* on the app (vs the data-layer record view) is not clearly documented — UNVERIFIED; week-1 spike item #2. Fallback if it doesn't: re-print asset labels as record-URL QR codes and scan with the phone camera app (violates the "associate existing labels" clause and adds a relabeling project).
- Transfers: `Transfers` + `TransferLines` with PENDING→ACCEPTED/DECLINED/CANCELLED single-selects; recipient's My Day shows "Waiting on you"; **Accept = open card → tap Accept button → confirm ≈ 3 taps** — parity with R-CUST-2's number is plausible here because it's a single button, not a form. Entire-rig transfer flips ownership via automation (reassign PRIMARY assignment); the dialog-says-so-in-plain-words requirement becomes button confirmation copy.

## 4. Evidence (GPS, photos)

- **Airtable has no location field type and no GPS capture on forms or records** — it is a years-open product-ideas request [C29]. Passive GPS-on-check (R-EVID-1, R-MAP-1's data source) is therefore **not natively possible**. Mitigation: route the daily check through a third-party form vendor (miniExtensions sells hidden-GPS-field collection for Airtable forms [C29]) — but that abandons the native-app flow §2 is built on, adds a vendor, and runs in the browser. Pick one: native app without GPS, or web form with GPS and a worse everything-else. I recommend native-app-without-GPS and concede the map/attestation lane (the D2 anti-goal is at least trivially honored: no tracking of any kind).
- Photos: attachment fields in forms/app work; server-side EXIF/GPS stamping and 1200px/85 compression do not exist (uploads are stored as-is); magic-byte validation, five-context photo model, and signed-URL privacy discipline are replaced by Airtable's attachment ACLs + expiring URLs [C23].
- Timestamps: created/modified times are server-side and reliable; **revision history 1 year on Team AND Business, 3+ years only on Enterprise Scale** [C9] — against the 3-year retention rule (R-DATA-2), append-only *event tables* (CheckLog, PortalEvents, RequestLineEvents) carry the audit burden instead of revision history, which is the right design anyway.

## 5. Offline — stated exactly, no flinch

What happens today with no signal, per official docs and dated community evidence:
- Official technical requirements: **internet access required on every platform; "Offline access to Airtable is not supported"** — the FAQ's only offering is CSV export for offline *reference* [C13].
- Interfaces and Forms are unavailable offline; no capture, no queue, no replay (community, Jan 2024, zero official replies) [C14].
- The mobile app has no documented offline cache contract; field reports (Feb 2026) describe edits lost *silently* even on Wi-Fi, and community experts state "Airtable has never really prioritized the mobile experience" [C15].

Consequences against the register: **R-OFF-1 through R-OFF-7 are unmet and unmeetable on current Airtable** — no outbox, no idempotent replay, no 401-parking, no lie-fi timeout discipline, no offline reads, no correct-template offline form, no late-replay date semantics (nothing replays), no observability of a queue that doesn't exist. The compensating *operational* design, offered honestly as a downgrade: a printed paper day-card per crew + a "signal debt" ritual (submit checks/custody events when signal returns, with the check's true date typed into a date field — trusting the operator's typed date with no bounded-window server clamp, weaker than D26), plus an SMS-to-admin fallback lane. That is precisely the group-text-plus-paper incumbent AHITS was built to beat. If CUL005's mornings are genuinely zero-signal (the spike question), the capture layer fails the charter's P0 by construction.

## 6. Automations / alerting (~40 of the 50-per-base budget [C10])

- **Cron scans** (scheduled trigger, hourly — 15-min minimum exists but burns run quota [C12]): missed-check-by-cutoff (query eligible assignments minus today's checks; admin-held flagged), maintenance overdue, equipment not returned, low stock (quantity−reservedQty < threshold), insurance/registration 30d/7d, inventory drift checks (age-qualified), stale-damage nag, hold-TTL release.
- **Dedup**: before create, "find records" where sourceKey matches AND unresolved; skip if found. This is at-least-once application logic, not a DB nullable-unique constraint — a burst can double-create until a janitor automation sweeps; concede R-ALRT-1's "DB-enforced" clause, keep its behavior in the common case.
- **Auto-resolve**: state-transition automations (check submitted → resolve missed-check alert; PIN…/account unlock n/a; request fulfilled → resolve; return received → resolve).
- **Dispatch**: admin email via the email action (Team caps 100 unique non-collaborator recipients/day, Business 1,000 — fine at this fleet size [C11]); operator-facing "bell" = an `Alerts`-driven "Waiting on you" block on My Day + optional email. Native push notifications for custom events are not a designed surface; deep links go to interface record URLs.
- **Run budget is a real constraint**: at 90 operators in season, per-record transition automations (~4 per check × ~5k checks/mo) + hourly crons (~15 automations × 720/mo) + transfers/requests/time entries lands ~50–100k runs/mo — **above Team's 25k cap, at/near Business's 100k, comfortable only on Enterprise Scale's 500k** [C10]. Mitigations: consolidate into fewer scripted automations, hourly-not-15-min crons, batch scans.
- DST caveat: scheduled triggers don't auto-handle DST transitions [C12] — the missed-check cutoff shifts an hour twice a year unless hand-adjusted.

## 7. Auth & onboarding for churning contractors

Conceded up front: **no PIN auth, no text-distributed tokenized invites**. Path A operators need an email-based Airtable account (the pilot roster does all have gmail addresses, so it is *operable*, just against R-AUTH-1's design intent for 20–90/season churn); password resets become the support verb PIN-reset used to be. Suspend = remove collaborator (effective on next request); seat is reusable, so churn costs seat-swaps, not new spend. Account-action audit trail: **Enterprise Scale only** (audit logs/SCIM/DLP) [C26]; on Team/Business, offboarding discipline is a checklist, not a log. Forced-PIN-change, tokenVersion-style instant fleet revocation, lockout-with-admin-unlock: none exist in this vocabulary; Airtable's own account security replaces them.

## 8. Integrity (the constraint honesty section)

Airtable has no unique constraints, no partial unique indexes, no transactions, no state machines, and no schema-migration safety gates. Every R-DATA-1 invariant becomes an automation: (vehicle,date,operator) daily-check uniqueness → on-create find-duplicates → flag `DUPLICATE` + alert (surfaced, not rejected; two racing writers both land); one open rig-vehicle per vehicle → same pattern with a janitor; serial-unique-within-item → same. Blast radius when the race hits: minutes of dual-truth until the janitor flags it, vs Postgres's reject-at-write. Schema changes are click-operations with 1-year (Team/Business) revision/snapshot restore [C9] — no CI migration gate, no DROP guard, but also far less to get wrong; "who stops a destructive change" = workspace admin permissions + snapshots. Backups/PITR/uptime are Airtable's by construction — a genuine R-OPS-1 point *for* this design (several of AHITS's own backup/restore-drill boxes are still unchecked as of 07-30).

## 9. External parties (hubs/shops) — R-PORT-1 approximation

- **Read**: free read-only share links per view (revocable by disabling the link), or free read-only portal users [C19].
- **Write-back**: per-record **prefilled public forms** — the work-order email carries `form?prefill_WO=recXXX&hide_WO=true` [C18]; submission appends a `PortalEvents` row; an automation applies the allowed transition to the parent WO (received/in-progress/completed; HUB_RETURN receipt + discrepancy path identical). Append-only, actor-labeled — the StatusLinkEvent shape survives.
- **What does not survive**: per-link capability security. The form URL is global; the prefill is guessable/alterable; there is no per-record token hash, no expiry, no ISSUED→…→REVOKED state machine, and a "dead" link cannot be made to stop accepting submissions per-record except by automation-side rejection *after* accept. For shops progressing work orders this is probably acceptable risk; **for the CC-17 INVOICE delivery channel it is not** — invoices go by email attachment instead (and note attachment URLs expire ≥2h [C23], so send the PDF as an email attachment, never a link).
- If tighter is wanted: Portals add-on gives authenticated external editors at ~$8/guest/mo effective (Team: from $120/mo for 15 portal seats; one portal per base) [C19][C21].

## 10. CC-17 Time/Invoicing (the roadmap load)

- **Clock**: My Day "Clock In" button → creates `TimeEntry` (start=now, task type picker with exception types Weather Delay/Breakdown/No Access/Travel/Rest one tap deep); "Clock Out" button stamps end. Tap parity with Clockify is *measurable and plausible* (two buttons/day + a picker) — **online only**. Offline clock-in/out riding an outbox (R-CC17-1's hard gate: "offline money-writes must not go live on an unverified offline base") **cannot be satisfied**: there is no offline base to verify. The A6-matrix gate would simply fail.
- **Rates**: automation resolves precedence (OperatorRate > TaskType default > base rate) at entry creation and writes an **immutable-by-convention `rateSnapshotCents` integer**; money math in scripting automations using integer cents (avoids float-summing; Airtable's number fields are otherwise floating-point). "Immutable" is convention + revision history, not enforcement — an admin editor can change it; field-editing permissions (Business+) narrow who.
- **Invoicing**: period compile automation → `Invoice` + `InvoiceLines`; **PDF generation is not native — Page Designer cannot be automated** (community-expert consensus, Aug–Oct 2025) [C24]; use DocsAutomator/DocuMint-class vendor (adds ~$50–150/mo, UNVERIFIED pricing) → attach PDF → auto-email to processing addresses (email action limits fine [C11]) → PAID back-write. Auto-increment via autonumber. Earnings-in-≤2-taps: a My Day "This week: $X" rollup — genuinely easy here.
- **Availability calendar**: native calendar interface layouts, operator self-marking + admin all-operator grid — **Airtable is *better* than unbuilt-AHITS at this row.**
- Missed-clock-out reconciliation: nightly automation flags open entries. Admin-held-rig exclusion (D3): filter on the assignment's admin-held flag in the compile — expressible, testable.

## 11. CC-18 week board — the clean win

Timeline-layout interface: deployments as rows × days, layering maintenance nextDue, rental windows, request neededBy, missed-check flags, (post-CC-17) availability; every chip click-throughs to the owning interface page. This is Airtable's native genre and beats a 2–4-week not-yet-built AHITS surface at near-zero build cost. One caveat: **Timeline layouts don't render in the mobile app** [C17] — the week board is a desktop/manager surface (which is what R-CC18-1 says it is).

## 12. Admin & reporting (the named driver — decisive win)

All 13 admin routes map to interface pages + views managers build *themselves*: filters, grouping, sorts, charts, CSV export, shared views — no code change, no Max-in-the-loop, and Omni builds new slices from a prompt [C25]. R-ADM-2's "AHITS builds new views slowly, one person" asymmetry is the honest core of the Airtable case, and the corpus itself always planned Airtable as the reporting/export target (PRD §9.3).

## 13. Scale envelope vs plan caps (R-SCALE-1)

Register estimate: 60–150k new rows/yr across hot tables at 90-operator scale, 3-year retention. Per-base caps: Team 50k (dies in season 1), **Business 125k (~1–2 seasons, then annual archive-base roll-off choreography that breaks live linked-record joins)**, Enterprise Scale 500k+ (~3 seasons clean) [C5]. Attachments fine [C6]. API 5 rps/base [C8] is irrelevant for native use, adequate for sync. Peak 6–7am concurrency is Airtable's SaaS problem, not ours — modulo the documented mobile-app reliability reports [C15]. Mobile interfaces are documented to degrade at "tens of thousands of records" in the app [C17] — My Day must be aggressively filtered/archived to stay small.

## Build estimate

To the best-achievable Airtable approximation (NOT full MUST-parity — R-OFF-1..7, R-AUTH-1/2, R-EVID-1 GPS, R-PORT-1 capability-URLs, and R-CC17-1's offline-clock gate are conceded, see residualGaps): ~10–16 weeks of a competent Airtable builder. Breakdown: week 1 = the two decisive field spikes (real-signal capture test on CUL005; barcode-in-interface verification) — a failed spike #1 should stop the replacement track and divert to the hybrid; weeks 2–3 schema + views; weeks 3–6 operator interfaces (My Day, check, scan, transfers) + admin interfaces; weeks 5–8 the ~40 automations (alert engine, transitions, holds, janitors, dedup) + external forms path; weeks 8–14 CC-17 (clock, rates, integer-cents scripting, PDF vendor integration, invoice email loop, availability calendar) — note CC-17 on AHITS is itself estimated 6–10 weeks, so Airtable is not obviously faster once money-grade care is applied; weeks 14–16 migration, parallel-run, training. Maintenance: the genuine win — the org's existing company-wide Airtable admin plus any power user can maintain views, automations, and churn-driven seat ops with zero code deploys and zero Max-only knowledge; the bus factor drops from 1 to 'whoever holds the workspace'. Offset honestly: a live operational base accumulates its own key-person risk in undocumented automation sprawl, and there is no CI, no test harness, and no migration-safety gate around any of it.

## Migration sketch

Do not cut over mid-operation. Sequence: (1) NOW (any decision outcome): stand up the reporting sync — nightly Postgres→Airtable API upsert of the ~10 reporting-relevant tables (1–2 wk; 5 rps/base is ample [C8]); managers get their views immediately, zero operator risk. (2) Season boundary only: freeze AHITS writes for a weekend; export Postgres tables to CSV/API-import into `AHITS Ops` (row volumes are trivial); re-upload evidence photos from Supabase Storage into attachment fields via API (mind per-base attachment quota [C6]; keep Supabase as the archival original — Airtable attachment URLs expire and 'Airtable as CDN' is officially discouraged [C23]). (3) Identity: create operator accounts/seats, run one supervised onboarding day per crew (email+password support burden replaces PIN resets — plan for it, churn makes it recurring). (4) Custody state: re-verify open custody (checked-out units, open rigs, holds) by physical spot-check during the freeze — automation-enforced invariants start from a human-verified baseline. (5) Keep AHITS read-only on Cloud Run for the 3-year retention window (R-DATA-2) or bulk-import CheckLog/audit tables into the Archive base; do NOT delete the Postgres instance — it is the operation's evidence base and the rollback path. (6) Rollback play: AHITS stays deployable for one full season; if week-2 adoption or lost-capture incidents trip the same P0 tripwire the charter defines, reverse the sync direction and return. Hard blocker to schedule around: if migration lands mid-CC-17 build, the money loop's incumbent (Clockify) must keep running until the Airtable invoice pipeline passes one zero-corrections payroll period (R-CC17-2's acceptance), exactly as AHITS would have had to.

## Hybrid option

The strongest honest play, and my actual recommendation given the offline findings: **Airtable as the manager/reporting/planning layer over AHITS capture** — which is literally what the corpus always planned ('Airtable sync for reporting/export', PRD §9.3; explicitly out-of-scope only as a V1 system of record, PRD §14). Mechanics: a one-way nightly (or hourly) sync job — Cloud Run cron reading Postgres, upserting ~10 denormalized reporting tables (checks, custody log, deployments, requests, maintenance, alerts, and post-CC-17 time/invoice rollups) into one Airtable base via the Web API (5 rps/base, well within Team's 100k calls/mo at this volume [C7][C8]). What it buys: (1) the named driver — managers get views/filters/ad-hoc reports/charts/CSV in the tool they already know, self-serve, this month, without waiting on Max's build queue; (2) R-CC18-1 essentially free — a timeline interface over synced deployment/maintenance/neededBy dates IS the week board, months before AHITS would build one, with the falsifier ('does the ops lead's Monday start here?') cheaply testable; (3) org-familiarity credit and a real answer to stakeholders without touching a single operator MUST — offline capture, PIN auth, custody invariants, portals, and the money path stay on the system engineered for them; (4) a live evaluation: if managers thrive in the Airtable layer, the company learns something real about a future fuller migration at near-zero risk. Costs: 1–2 weeks to build the sync + mapping; ~$0–275/mo marginal (2–5 admin/manager seats on the existing org plan — read-only consumers are free [C4], seats only for managers who edit annotations); a small maintenance surface (schema drift between Prisma and the synced tables — regenerate mappings when migrations land); one-way discipline (Airtable-side edits are annotations, never written back to the system of record, so no write-conflict class exists). Limits that matter: sync freshness is minutes-to-hours, not live; record caps eventually require archiving the synced base too [C5]; attachment sync should copy thumbnails only (quota + URL-expiry [C6][C23]). Verdict in one line: the hybrid wins driver #1 and #2 outright, costs ~2% of the replacement's risk, and concedes nothing on the register.

# Google AppSheet — Enterprise Plus on Cloud SQL for PostgreSQL (Core-on-Sheets priced as the degraded variant; Looker Studio as the reporting layer)

## Design

# AHITS on Google AppSheet — the champion design

## 0. The architecture call that everything hangs on

The only AppSheet design that survives this register is **Enterprise Plus on Cloud SQL for PostgreSQL** — not Core-on-Sheets, and not AppSheet's own database.

- AppSheet's native database is disqualified by arithmetic: 2,500 rows per database on Core, 200,000 on Enterprise Plus, 20 tables per database, 100 columns per table (support.google.com/appsheet/answer/12653576, fetched 2026-07-31). The register's envelope (R-SCALE-1: 20k–50k daily-check rows/yr, hot tables reaching low-to-mid hundreds of thousands of rows over 3 seasons under 3-year retention) eats the Core allowance in the first month.
- Google Sheets as backend survives longer (guidance: don't exceed 100K rows; app payload capped at 5–10MB compressed on device — answer/10104789) but forfeits the two things this register is actually about: database-enforced invariants and an API. Both are Enterprise-Plus-only capabilities anyway (external databases and the AppSheet API are Enterprise Plus exclusive — answer/10105400, answer/10105398).
- **Cloud SQL Postgres keeps AHITS's constraint layer alive.** This is the champion's central move: the partial unique index on open rig-vehicles, the `(vehicleId, date, operatorId)` unique daily check, serial-unique-within-item, one-unresolved-alert-per-source — all of R-DATA-1's DB-enforced integrity migrates as SQL, not as builder expressions. AppSheet becomes a client; Postgres remains the law. When two raced writes collide, the second one **fails at sync with a surfaced error** — never a silent merge. (What that failure UX costs is conceded honestly in §8.)

Topology: **two AppSheet apps + one reporting layer.**
1. **AHITS Field** (operators): security-filtered to my rig, my checks (last 14 days), my transfers/requests, cached catalog slices — keeps the on-device payload far under the 5–10MB compressed cap (answer/10104789). Runs in the AppSheet host app installed from the App Store / Play Store (answer/10105388).
2. **AHITS Admin** (admins, hub staff): full tables, desktop mode + phone.
3. **Looker Studio on the same Postgres** (free-tier product; Google-built PostgreSQL connector, TLS, 150K-row query cap per query — docs.cloud.google.com/data-studio/connect-to-postgresql) for the ad-hoc reporting appetite, plus direct SQL for anyone who can write it.

Schema: a near-1:1 port of the Prisma model, ~30 tables (users, vehicles, inventory_items, inventory_units, inventory_stock, rigs, rig_vehicles, kit_items, daily_checks, custody_events, transfer_requests, transfer_lines, handoffs, maintenance_tasks, maintenance_schedules, requests, request_lines, line_events, alerts, notifications, email_log, settings, checklist_templates, + the CC-17 set: task_types, operator_rates, time_entries, expenses, invoices, invoice_lines, availability). Two deliberate flattenings: (a) the daily-check checklist JSON becomes ~25 fixed Yes/No/N-A columns with data-driven `Show_If` per vehicle type (see §3); (b) costs/rates live in **separate admin-only tables** joined by Ref, because AppSheet has no true column-level security — security filters are row-level (answer/10104488), so the operator cost-lockout (R-ADM-1) is enforced by table split + filter, server-side.

**Design law #1 (imposed by the platform): everything stateful is event-sourced.** AppSheet's concurrency model on a shared row is last-write-wins with no overwrite prevention — community-confirmed as current behavior in a March 2026 thread whose scenario is literally gear custody state (discuss.google.dev/t/offline-sync-concurrency-issue-preventing-last-write-wins-overwriting-valid-state/341758). The community's own remedy — append event rows, never edit shared state; derive status server-side — is AHITS's own CheckLog philosophy, so the port is philosophically clean: every check-out/in, transfer action, draw/restore writes an immutable `custody_events` row keyed by `UNIQUEID()`; unit/vehicle status columns are updated only by server-side bots (single writer) and backstopped by Postgres constraints. Offline replays of the same event row carry the same key → the DB unique index makes replay idempotent at the data layer, on top of AppSheet's own platform idempotency ("even repeated sync retries will not cause duplication or corruption of data" — answer/10107724).

## 1. Offline — argued at champion depth, because this is where the fight is

AppSheet's documented offline machinery is the same shape as AHITS's charter, in Google's own words:
- "All changes are made locally and are queued up to send over the network when you choose to Sync… During Sync, if any changes fail to be propagated, they are retried… changes are idempotent" (answer/10105762).
- "AppSheet automatically queues changes and defaults to delayed sync behavior **to prevent the loss of data**" (answer/10107724).
- "All changes are recorded locally on the device. Even if the device shuts down and restarts, the changes still are available… any data captured by the app should never be lost" (answer/10104788).

**Lie-fi (R-OFF-2) is a structural match-or-better.** AppSheet is local-first: Save commits to the on-device store instantly and sync is a separate, retried, backgroundable act. The AHITS failure mode CC-29 had to engineer away — operator staring at a disabled "Submitting…" for 60s and swipe-killing the form — cannot occur, because there is no network on the Save path at all. AHITS needed 12s/20s timeouts to approximate what AppSheet does by construction. Swipe-killing the app after Save loses nothing (queue survives restart, documented above).

**Late-replay date semantics (R-OFF-4):** the check row's `[Date]` is stamped by `TODAY()` as an initial value **at capture**, not at sync; the queued add replays with its captured values, so a day-N check synced on day N+1 files under day N. A collision with an existing `(vehicle, date, operator)` row fails the Postgres unique index → surfaced sync error, never a silent upsert-merge. (Delta: AppSheet has no upsert, so same-day re-entry is an *edit* of the existing row rather than an idempotent resubmit; and the 3-day-past-window clamp becomes a `Valid_If` at capture rather than a server clamp — weaker against a device with a wrong clock. Flagged, not fatal.)

**Offline reads (R-OFF-6):** table data is cached on device by design; the form opens and saves with zero network; QR scans resolve against cached rows; the correct per-vehicle-type checklist renders because `Show_If` reads the cached `checklist_templates` table, not a hardcoded default. Freshness stamping: AppSheet shows last-sync state natively (weaker than AHITS's per-surface "Data as of HH:MM," but present).

**The four honest offline deltas, priced:**
1. **First-launch-online is a documented precondition:** "the app must initially be launched on the device when it is online" (answer/10107724). Manageable procedurally — onboarding already happens in signal (AHITS's install + first login needs network too) — but it is a rule the one-pager must carry.
2. **Browser-tab operators are disqualified from evidence capture.** In a browser, offline works but "offline image and document caching will not work" (answer/10107724), and — the disqualifying sentence — for browser image capture "the new or updated record with the image must be synced to the backend *before* the browser tab is closed. Otherwise, the captured image content will be lost" (answer/10106529). Some of this cohort runs browser tabs today (UX review §8). **The design therefore mandates the host app for all operators, full stop** — an org-discipline cost AHITS doesn't impose.
3. **App-definition changes while changes are queued is AppSheet's version-mismatch write-loss path:** "This change cannot be applied because there is a newer version of your app… The local changes queued on the device cannot be applied by the server"; recovery is a `_recoveryData` JSON folder manually re-applied, or the user emails "Show Changes" then "Reset Changes" (answer/10105777). Data is recoverable-but-manual — which under the charter's definition is still a P0 incident. Mitigation is real but organizational: AHITS's own evening-deploys-only rule becomes iron law (no editor touches during field hours), and the checklist-template design (§3) keeps routine admin config in *data*, not app definition, precisely to shrink this surface.
4. **Outbox observability (R-OFF-7) is coarser.** The operator sees an unsynced-change count and can view changes, but per-item Retry/Discard does not exist — the mobile recovery verbs are "Show Changes" (email them) and "Reset Changes" (discard **all**) (answer/10105777). Server-side, Enterprise Plus Audit History records every sync/add/edit/delete with user identity for 53 days with filtering/analytics (answer/10104794), and because truth lives in Postgres, the written lost-write reconciliation queries ("operator says they submitted X") port verbatim as SQL. No Sentry-grade tripwire on device-side queue anomalies; that concession stands.

Also on the risk ledger: a live, unresolved community bug report (June 2026) of image uploads failing/very slow on cellular data after a host-app update (discuss.google.dev/t/bug-report-image-upload-fails-on-mobile-data-cellular-after-app-update-june-1-2026/372469) — a reminder that on AppSheet, field-critical client bugs get fixed on Google's timeline, not yours. That cuts both ways (they also fix them without you), but for a rural-cellular fleet it is a real dependency.

## 2. Auth & onboarding for churning contractors

AppSheet requires provider sign-in for any app with attribution: supported providers are "Apple, Box, Dropbox, Google, Microsoft, Salesforce, Smartsheet," selectable as "Any provider" (answer/10104975). The **no-sign-in tier is disqualified for custody exactly as the brief predicted**: "USEREMAIL() and USERNAME() do not have a defined value if the app does not enforce user sign-in," audit identity degrades to `-1` (answer/10104975, answer/10104794). So every operator signs in.

The champion's evidence-based counter to the "contractors can't do accounts" objection: **the pilot's own charter roster is 8 personal Gmail addresses + 1 agricarbon.co.uk** (AHITS_PILOT_CHARTER.md §1). Every Android phone has a signed-in Google account by construction; every iPhone has an Apple ID; AppSheet accepts both. Onboarding one-pager: (1) admin adds the operator's email to the app allowlist; (2) text them the install link; (3) they install the AppSheet host app from the store (answer/10105388), open the link, tap "Continue with Google/Apple" using the account already on the phone. Zero new passwords, zero PIN resets ever, no lockout ladder, no CGNAT-shared rate-limit bucket (the R-AUTH-1 known seam simply evaporates — account security is Google's/Apple's). Suspend = remove from allowlist; invite = add a row.

Conceded deltas: **revocation is sync-time, not instant** — a removed operator's device keeps its cached data and queued state until the next sync attempt fails; there is no tokenVersion-style same-request kill (R-AUTH-2 timing conceded; no official doc found on revocation latency — UNVERIFIED beyond "access is enforced at sync"). Shared-phone crews are *worse* than AHITS (switching a signed-in Google account mid-shift is heavy ceremony vs re-entering a PIN). PIN-as-such (R-AUTH-1) is conceded as replaced-not-reproduced; the claim is equivalence-for-purpose, and it should be tested on real contractors before being believed.

## 3. The operator's day, tap-counted

**Today (R-FRIC-3):** the app's start view is a card/deck "Today" composed from security-filtered slices: one contextual primary card (Start daily check → You're set), per-vehicle check state (virtual column: does a check row exist for me+vehicle+TODAY()), "Waiting on you" transfer cards, awaiting-pickup cards with hold context, my open requests. It assembles the day, not a menu — a real AppSheet pattern, though visually it is AppSheet's chrome, not AHITS's tuned one.

**Daily check (R-FRIC-1), step by step:** open host app (Today renders from local cache instantly) → tap the vehicle's Start check action (tap 1) → form opens pre-filled: vehicle + operator from context, `[Date]`=TODAY(), `[Site]` initial value = my most recent check's site (MAXROW lookup — carried forward like AHITS), `[StartedAt]`=NOW() (duration instrumentation, see below), `[GPS]` LatLong initial value `HERE()` — populated from the last polled location (polled once per minute; answer/10106789), so GPS is passive and never blocks the save (R-EVID-1's resolve-or-skip semantics, with accuracy honestly lower than AHITS's warm-capture: `HERE()` is "recommended [against] where high accuracy is especially important"). Checklist: ~16 Yes/No/N-A enum rows **defaulted to Yes** — the same posture as AHITS, whose own wizard defaults to all-Yes (2026-07-28 review §1.7 describes wipes "to all-Yes") — operator flips only exceptions; a "No" reveals a required note + photo via `Show_If`/`Required_If` (R-MNT-1's capture path). Odometer: Number column, 5 keystrokes; warn-only sanity is a `Show_If` warning label comparing to the last reading (AppSheet's `Valid_If` blocks, so warn-never-block needs this workaround — noted). Save (tap 2), commits locally instantly. **Happy path ≈ 2–3 taps + 5 keystrokes + a review scroll, ~35–50s** — inside the 90s PRD ceiling, credibly near the 35s number, and it must be stopwatch-verified on a real phone in glare before anyone signs it. Pencil-whip instrumentation ports: duration = SavedAt − StartedAt (bot stamps SavedAt), the <20s flag and adoption denominator become Looker Studio tiles over Postgres (R-ADM-3 largely reproducible; snapshot-per-day eligibility is a SQL view).

**QR (R-QR-1):** barcode/QR scanning is Core-tier-and-above and **mobile-app-only — "Scanning is not supported when running an app in a web browser"** (answer/10106618; plan gating answer/10105400). A Scan view drives a Scannable text column; the scanned code resolves against the cached asset table (works offline, sub-second on cached data) and lands on the asset detail, whose row-level actions are conditioned on status: Available→Check Out; Checked Out→Check In / Report a problem; Vehicle→Start Daily Check — the scan-to-action routing the register demands. Association at creation: type-or-scan into the barcode column; Postgres unique index gives the 409-on-conflict. Torch/manual-entry: manual entry always (it's a text column); torch is host-app camera behavior — UNVERIFIED, flag for the device pass.

**Transfers (R-CUST-2):** TransferRequest + lines; recipient's Today shows the card; Accept = one grouped action (status flip + custody_events rows + note), 3 taps end-to-end with no confirm dialog. Entire-rig vs selected-gear is one entry with two branches (D22's flow), and the ownership-flip consequence sentence is the action's confirmation text. Decline/cancel restores the exact units because the events carry unit ids — the §1.9-class bug is structurally excluded by event sourcing. Photos ride as Image columns.

**Photos (R-OFF-5/R-EVID-1):** camera or camera-roll on mobile (answer/10106529); Image upload size set to High (1600px) ≈ AHITS's 1200px policy; images captured offline queue with the record and upload at sync (host app only — see §1 delta 2). Files land in the creator's cloud storage since the backend is a database ("they do not have a file system… stored in your primary AppSheet account's cloud storage" — answer/10106598) — i.e., Drive under an org account, access mediated by the app. Per-photo bounded-retry-with-named-failure and dead-ref 422 rejection (the CC-29 photo-wedge class): **no documented equivalent — conceded.** Whether a persistently failing photo blocks later queued changes is not documented either way; it must be tested in the A6-equivalent matrix, and the champion does not claim it.

## 4. Custody, inventory, maintenance, requests

- **R-INV-1:** serialized vs consumable is native relational modeling: inventory_units rows (per-unit QR/serial/status/soft-delete) vs inventory_stock rows (hub × item, quantity + reservedQty); availability is a SQL view. No fake flat table.
- **R-CUST-1:** the custody state machine runs on custody_events + bot-derived status; **the one-open-rig-vehicle-per-vehicle partial unique index survives verbatim in Cloud SQL** — the invariant stays in the database, exactly as the register demands. Raced writers: loser's change errors at sync (surfaced), admin fixes; what happens to the *rest* of that user's queued changes when one change fails is not precisely documented (retry continues; structural mismatches "will continue to fail" — answer/10104788) — the head-of-line question must be empirically tested; conceded as unknown.
- **R-MNT-1:** maintenance_schedules with MILEAGE/DAYS/MONTHS intervals; nextDue/nextOdometer derived by bot from the daily check's odometer; "Report a problem" is one action (what + photo + note + still-usable toggle); admin triage in a two-click detail view; stale-damage nag is a scheduled bot; shop emails via automation.
- **R-REQ-1:** requests + request_lines with line-level confirm/edit/deny/substitute actions writing line_events (append-only); reservedQty holds enforced in SQL with a TTL sweep bot; **the materials-request reply loop closes on day one** (fulfillment bot notifies the requester — the leg AHITS currently loses to texting is a one-bot fix here; push notifications via the automation notification task, 60k/day cap — answer/11828262).
- **R-ALRT-1:** scheduled bots (Core+; answer/10105400) run the cutoff scans — missed-check-by-cutoff (business-date-aware SQL against active rigs, admin-held flagged via deployment_assignments), maintenance overdue, insurance/registration 30d/7d, low stock, drift INV-1..5 (age-qualified in SQL). Bot execution has a 5-minute cap with 3 retries (answer/11547468) — trivially sufficient at this scale; process-execution quota 500k/day (answer/11828262). **Dedup is DB-enforced**: nullable-unique activeKey in Postgres, the bot checks-then-inserts with the index as backstop; auto-resolve bots ride the state transitions. Dispatch: email task (Core quota 1,000–20,000 recipients/day; Enterprise 50,000 — answer/11828262) + push notifications deep-linking via LINKTOROW into the opened record. Cadence floor: scheduled events are documented at daily granularity in the official doc; sub-daily/hourly scheduling is community-discussed but not officially enumerated — UNVERIFIED; the register's alerts are daily-cadence, so this bites only the cron-dead-man ambition (see gaps).

## 5. External parties (R-PORT-1) — the honest concession, sized precisely

There is **no AppSheet equivalent of the capability-URL StatusLink**: a scoped, sha256-hashed, expiring, revocable, single-record token with a write-back state machine and an actor-labeled event log. The no-sign-in options fail the bar by documentation: public apps have no user identity (audit `By User = -1`), no per-token scoping, and Publisher Pro is per-app licensing for apps where "you do not need to restrict app access to particular people" (answer/10105400) — auditless and unscoped, disqualifying for custody. Conceded outright.

What shrinks the concession is the corpus itself: **D21 froze the portal's RESERVATION channel because all hub staff have accounts**, and **D29 deprioritized the shop portal** ("we're not currently pushing anything to repair shops"). So the *live* portal load is hub-return receipts (hub staff → licensed users or User Pass consumers in the Admin app, ~$5/user-month community-priced, official price UNVERIFIED) and work-order progress (stays on email: automation sends the work order; the shop replies by email; admin records status in ≤2 clicks — D29's own accepted posture). The **INVOICE delivery channel needs no portal at all**: the deliverable is a PDF, and AppSheet emails it (§6). Residual truth: if the org ever needs shops acting on links with no accounts again, AppSheet cannot do it and a side-service must be built — the requirement is conceded, not met.

## 6. CC-17 — the money loop, claimed with its gates

- **Clock:** clock-in/out actions writing time_entries (timestamps = NOW() at tap, captured on device, offline-queued through the same documented queue as everything else — R-CC17-1's "same outbox from day one" is satisfied by construction). Task types incl. Weather Delay / Breakdown / No Access / Travel / Rest Day as enum buttons one tap deep.
- **Rates:** a server-side bot resolves precedence (OperatorRate > TaskType default > User.hourlyRate) at entry creation and writes **immutable snapshot columns**; totals are **Postgres views — SQL-computed sums, never client floats**, meeting D19's arithmetic rule *better* than any spreadsheet-tier tool could.
- **Invoicing (R-CC17-2):** a period bot compiles hours × snapshots + expenses → "Create a new file" task renders a **PDF from a Google Docs template** (Core+; 2,500 PDFs/day cap — answers 11512511/11828262) with an auto-incremented number (Postgres sequence) → operator submit / admin approve actions → automation emails the pre-configured processing addresses → PAID back-write by admin action; an email_log table written by the same bot is the EmailLog analog (bot run history retains 55 days; the table retains forever). Operator earnings view: a Today card summing my period from a SQL view — ≤2 taps.
- **Availability:** table + calendar view; the admin all-operator week *grid* is weak in AppSheet — Looker Studio or a Sheets pivot carries it.
- **The binding gates transfer, not dissolve:** D13's full 28-row × 5-target offline matrix has *never been run against AppSheet* — offline money-writes must not go live on an unverified offline base, and that verification is a genuinely open empirical question here (browser rows fail by documentation already). D19 rider 1 (tap parity with Clockify, measured) and D3 (admin-held exclusion in the SQL attribution view) are both implementable and must be verified at review. Estimate: 4–6 builder-weeks on top of the base build.

## 7. CC-18 + the reporting appetite (named driver #1) — where this design flat-out wins

Managers get four layers AHITS builds one code-change at a time: (1) AppSheet Admin desktop views — tables, slices, filters, group-bys, detail drawers, inline edit; (2) **Looker Studio over the same Postgres** — drag-and-drop ad-hoc dashboards, the pilot metrics tiles, scheduled email reports (Google-built Postgres connector; 150K rows/query cap — fine at this scale); (3) raw SQL for anyone who can write it; (4) CSV export everywhere. The CC-18 week board lands as a Looker Studio timeline/pivot over rigs × days with maintenance-due, neededBy, rental windows, missed-check flags — read-only by construction, click-throughs to AppSheet deep links — **available in week one, not "2–4 weeks, queued after CC-17."** R-ADM-2's row is won decisively; the register's own function — pricing what must not be lost to win it — is answered in §8.

## 8. What the champion signs, and what he refuses to sign

Signable at champion confidence: the offline *capture* loop for host-app operators (documented queue semantics + local-first save), Cloud-SQL-enforced invariants, event-sourced custody, QR scan-to-action, passive GPS/photo evidence, churn-tolerant provider auth for THIS cohort, the alert engine at daily cadence, PDF invoicing with SQL-grade sums, and a manager/reporting layer strictly better than AHITS's. Bus factor: Google maintains the runtime, client, sync engine, and stores; an ops-literate admin can maintain views/slices/data; the builder-grade layer (bots, SQL, security filters) still needs one owner — the bus factor shrinks from "one person owns a codebase" to "one person owns a configuration," which is a real, honest reduction, not an elimination.

Refused: the four seams don't all close. The **portal** is conceded (narrowed by D21/D29, not closed). The **zero-lost-writes charter as written** is not met — version-mismatch recovery is manual, per-item Retry/Discard doesn't exist, photo-failure isolation is undocumented, and browser-tab image capture is documented data loss; "recoverable with admin effort" is below the charter bar even when nothing is ultimately lost. The **UX floor** (44px targets, AA amber, back-gesture guards, quiet updates, 320px arithmetic) is Google's to set, not ours — the register's R-UX-1 items were each *observed* to destroy work for this cohort, and on AppSheet you cannot patch them, only file tickets. And **friction parity is a claim pending a stopwatch**, not a fact: nobody has tap-counted an AppSheet daily check in glare with gloves, and the champion's ~35–50s estimate must survive that measurement or the adoption thesis fails exactly as D5 predicted for static menus.

Net position: this is the strongest honest "stop building, configure" design that exists. It carries both loops and the roadmap load at daily-operations grade, wins reporting outright, and kills most of the bus factor — **at the price of the charter's letter on offline observability, the portal, the UX floor, and an unrun offline verification matrix.** If the org will not pay those four prices, the category is closed and AHITS's build justification stands.

## Limits that bite at the register's volumes (R-SCALE-1)
- **5–10MB compressed per-app on-device data cap** (answer/10104789): forces security-filtered slicing of operator data (own rig, 14-day check window) and annual archive tables for 3-season history. The full-history admin experience lives in Looker Studio/SQL, not in the synced app.

The honest pricing argument for AppSheet is not the license line; it is retiring the single-maintainer engineering time and Google absorbing the ops floor (backups/PITR/uptime/client updates — most of R-OPS-1 by construction). ## Migration sketch

Cutover between seasons, never mid-operation — a rolling-start pilot on CUL005 makes mid-season migration indefensible. Phase 0 (1 wk): stand up Cloud SQL Postgres; pg_dump/restore from Supabase; write the two flattenings (daily-check checklist JSON exploded to fixed columns via script; costs/rates split to admin-only tables); leave historical photos in Supabase Storage and map their URLs into Image columns (AppSheet renders external URLs), new photos land in Drive. Phase 1 (build, per estimate) against a copy of live data — the builder works on real custody history from day one. Phase 2 (2 wks, parallel run): 2–3 friendly operators run BOTH apps daily (double-entry acknowledged as the cost of truth); compare rows nightly in SQL — checks, custody events, GPS presence, photo attachment rates; run the offline device matrix on their actual phones; stopwatch the daily check. Phase 3 (cutover weekend): freeze AHITS writes Friday evening; final delta sync; Monday operators onboard via the one-pager (install host app, open link, sign in with the Google/Apple account already on the phone — identity mapping is PIN-account → operator email, already known from the roster); AHITS stays up READ-ONLY for one full season as the dispute/evidence archive (3-year retention rides the Postgres data either way, since Cloud SQL now holds the same rows). Rollback play: AHITS's codebase and Supabase remain intact through season one — reverting is re-pointing operators at the PWA and replaying the delta from Postgres (both sides are the same schema family by design). Named migration risks: checklist-JSON explode must preserve per-item answers for the variance/evidence record; open in-flight state (pending transfers, unreturned units, holds with TTL) must be migrated as OPEN events, not re-created by hand; and the queued-outbox contents of any operator phone at freeze time must be flushed in AHITS BEFORE freeze (an un-flushed IndexedDB outbox does not migrate — walk the fleet through a verified final sync, per the triage card).

## Hybrid option

The strongest partial adoption — and the champion's actual highest-EV recommendation if the residual gaps are dealbreakers: leave AHITS as the capture system (its offline loop is verified, tuned, and live) and buy ONLY the thing stakeholders actually asked for — the manager/reporting layer. Two rungs. Rung 1 (days, ~$0 license): Looker Studio pointed read-only at the AHITS Postgres (Supabase supports direct Postgres connections; create a read-only role, allowlist Looker Studio's published IP ranges, TLS) — managers get drag-and-drop dashboards, filters, scheduled email reports, the pilot-metrics tiles, and a CC-18-shaped week pivot over rigs × days THIS WEEK, with zero writes anywhere near the custody path; cost ≈ 2–4 days of Max's setup + dashboard time. Rung 2 (1–2 wks, ~$60–100/mo): an AppSheet Enterprise Plus ADMIN app (3–5 seats × $20) on the same read-only Postgres for phone-native admin consumption — bell-style notifications, mobile-friendly drawers over deployments/inventory/maintenance, saved slices managers build themselves without a Max code change; writes stay in AHITS (the app is read-only by role), so no write-path bifurcation, no offline-matrix re-verification, no operator retraining, no migration risk. What it buys: named driver #1 (views/filters/ad-hoc) at Airtable-class quality, organizational familiarity via a Google-branded surface, CC-18 essentially free, and a live evaluation of AppSheet against THIS data before anyone bets the capture loop on it. What it costs: ~$720–1,200/yr + a read-replica's worth of DB hygiene + one more surface under the evening-change rule. What it does NOT buy: any reduction in the capture-side bus factor — AHITS's outbox, PIN auth, portal, and PWA remain Max-maintained. This is also exactly the integration posture the corpus itself always planned ('Airtable sync for reporting/export', PRD §9.3) — read-side reporting was conceded to somebody else's strength from the start; this hybrid just picks Google's version of somebody else.

# Fulcrum Elite (native-app field capture) + company's existing Airtable (admin/reporting/week-board) + a custom glue service (invariants, alert cron, sync) + Clockify retained (time/invoicing conceded)

## Design

# Fulcrum replacement design for AHITS — the honest steelman

## 0. The thesis, stated without varnish

Fulcrum attacks AHITS at its crown jewel from the opposite direction. The hardest engineering in AHITS — the offline outbox — shipped with at least five silent write-loss/duplicate mechanisms that a dedicated adversarial review (2026-07-28 §1.1–1.6) plus packet CC-29 had to find and close, the full A6 offline matrix (28 rows × 5 targets) has *still never run* (parked to pre-CC-17, D13), and the queue engine had zero automated coverage until CC-29 added the fake-indexeddb harness. Fulcrum's entire product is that layer: **native iOS AND Android apps** (not a PWA — no service-worker update toasts eating Submit taps, no hydration-fossil desktop shells, no iOS tab-eviction, i.e. the whole UXP-1 class of defects doesn't exist), receipted offline create/edit with photos, offline GPS, offline basemaps, data events running on-device in disconnected environments, and auto-sync the vendor states happens "without any loss" (fulcrumapp.com blog, 2024-08-08). Records save **locally, always, instantly** — there is no "Submitting…" state to swipe-kill on lie-fi, so R-OFF-2's failure mode is absent *by construction*, not by a 12s AbortController someone had to remember to add.

The equally hard truth this design does not hide: Fulcrum is a field-data platform, not an operations system. The custody state machine, DB-enforced invariants, two-party transfer acceptance, tokenized no-account portal, the scheduled alert engine, and the entire CC-17 money loop are not in the box. They are either rebuilt as a glue service (same bus factor, smaller surface), degraded to convention, or conceded. §8 of this document and residualGaps state each one plainly.

## 1. Org structure (Fulcrum "apps" = form + record store; Projects scope everything to CUL005 etc.)

Eleven apps. Operator-visible apps are limited to five via per-app Member Permissions (app-level access control is native); everything carrying cost/spend data (unit cost, supplier, rental rates) lives in admin-only apps, satisfying the R-ADM-1 "operators never see cost" rule structurally.

1. **Daily Vehicle Check** (flagship, highest volume). Fields: vehicle (barcode field — scan the truck's *existing* QR label, or type it; Fulcrum barcode fields "retrieve or store a value" and support QR among 13 formats), site (text), odometer (numeric), the 16 checklist items as Yes/No/N-A choice fields **defaulted to Yes** (operator flips only the No's — same interaction shape AHITS measured), conditional required note+photo on any No (data-event visibility + INVALID validation, runs on-device offline), photos, notes. **Record geometry auto-captures device GPS at creation — passive, zero taps (R-EVID-1), and it works offline.** Per-vehicle-type checklist variants = sections toggled by data-event rules on the vehicle-type value; admin edits templates in the **form builder — no developer, closing R-ADM-1's template requirement natively** (D24's mounted Wintex/Giddings items are just more section rows). A computed status field (data event on save: any No → FAIL) drives the failed-check workflow.
2. **Vehicles** — registry, status, QR value, insurance/registration dates, rental window, last-known odometer (maintained by glue from checks).
3. **Inventory Items** (admin-only app: consumable flag, thresholds, reorder URL, supplier, unit cost).
4. **Inventory Units** — serialized: per-unit record, serial, QR barcode value, status enum (AVAILABLE/CHECKED_OUT/IN_MAINTENANCE/INOPERABLE/IN_TRANSIT/RETIRED), record-link to Item, damage history via linked Maintenance records. (R-INV-1's serialized half.)
5. **Hub Stock** — consumable qty + reservedQty per hub. **Only the glue service writes the arithmetic** (phones write Custody Events; glue applies them) — because Fulcrum has no transactions and concurrent edits to one record field-merge with last-write-wins, letting phones race the counters would corrupt stock.
6. **Custody Events** — the CheckLog analog and the operator's custody verb: scan unit/item QR into a barcode field, action (check-out/check-in/draw/return), qty, condition, photos, GPS auto. Glue consumes the webhook and flips Unit status / Stock counters — seconds later online, on-sync offline.
7. **Deployments/Rigs** — operator, vehicles (record links), kit as a repeatable section, project, started/ended.
8. **Transfers** — selected-gear list or entire-rig flag, from/to operator, status PENDING/ACCEPTED/DECLINED/CANCELLED, optional note presets, photos. Created record is **Assigned** to the recipient (record assignment restricts visibility to assignee + managers) and a Workflow fires an **SMS** to the recipient's phone (Workflows support SMS actions natively). Acceptance = recipient edits status to ACCEPTED. What this is NOT: an enforced two-party primitive — see §8.
9. **Requests** — reservation/material, repeatable lines (item/qty/line-status), neededBy; glue maintains holds and the reply-loop notification (an SMS on fulfillment — which, noted for fairness, would *close* the materials-reply loop AHITS itself currently loses to texting, UX review §3.2).
10. **Maintenance** — damage reports + scheduled tasks; MILEAGE/DAYS/MONTHS intervals with nextDue computed by data events on save; shop dispatch = Workflow email **with the per-record PDF report attached**.
11. **Incidents** — NS-13's shape (type/narrative/photos/GPS/parties). Trivial in Fulcrum and arguably better than AHITS's version, which does not exist.

## 2. Operator phone flow — the daily check, step by step (native app, offline-first)

1. Open Fulcrum (native app; no SW, no hydration, no update toast).
2. Tap **Daily Vehicle Check** from the app list. *(Concede: the home screen is an app list — this is the "static menu" D5 refused to launch on. There is no Today assembly, no per-vehicle done/due state, no contextual primary action. §8.)*
3. Tap **+** (GPS rides along passively).
4. Vehicle: tap the barcode icon → scan the truck's existing QR (works against locally-synced data offline) — or type the code.
5. Flip any No's (note+photo required inline); all-Yes days touch nothing.
6. Odometer (numeric). Inline sanity vs the vehicle's last-known value is feasible only to the extent data events can read the linked Vehicle record's field on-device — implementable but **not verified here**; worst case the sanity check runs in glue post-sync.
7. Site (typed; **no carry-forward** — data events cannot query yesterday's records on-device; mitigation is putting site on the Rig record and reading it via the record link, unverified).
8. **Save.** Local commit, instantly, regardless of signal. Sync fires automatically on save/app-launch/app-list navigation; photos "start syncing to the server as they are added to the record" to shrink loss windows.

Honest stopwatch estimate: **~7 taps + 5–10 keystrokes, 45–60s** vs AHITS's *measured* 5 taps + 5 keys / ~35s including nav (UX review §0/§3.7). Fulcrum loses the tap race (no vehicle preselection from a Today view, no site carry-forward) and wins the catastrophic tail (no lie-fi hang, no form-state destruction, no back-gesture wipe — native form state survives). Under R-FRIC-1's ceiling (90s on poor signal) it passes; against the 35s measured bar it does not, until proven on-device.

## 3. Offline, judged against the register's semantics (the case FOR, then the honest deltas)

**What's bought, engineering-grade and sourced:** offline create/edit; offline photo/video/audio storage in-app; offline GPS; offline basemaps (MBTiles layers, downloadable per device); **data events execute on the mobile device** (docs.fulcrumapp.com) and the vendor states they work in disconnected environments; auto-sync on reconnect "without any loss" (vendor claim, 2024-08-08 post). Sync runs automatically at sign-in, launch, app-list return, and record save; "Draft records will not be synced" (drafts are device-local by design). The five CC-29 failure classes map: photo head-of-line wedge (vendor-managed media pipeline, incremental upload), lie-fi hang (save is local — no hang state exists), concurrent-flush double-send (one vendor sync engine, not 2–4 hook instances), late-sync re-dating (client `created_at` is the capture-time timestamp, stored separately from `system_created_at` — the true day survives late sync), dead photo refs (media are first-class attachments, not string URLs).

**The deltas the antagonist will find anyway, conceded here first:**
- The specified R-OFF-1 *mechanisms* (IdempotencyKey body-hash 422, transient-409 vs terminal, 401-parking, per-item Retry/Discard outbox UI) are vendor-internal or absent. You get the intent (no lost writes) as a **marketing-page promise plus a decade of field deployments, not a testable contract you own**. When it fails, you file a support ticket instead of reading your own Sentry tripwire.
- **Conflict semantics are field-merge + last-write-wins on same-field edits** (official: "the data from the user who syncs last will overwrite the other"). This design makes operator conflicts structurally rare (every check/custody event is a NEW record with one author), but where AHITS surfaces a 409 on a late-replay date collision (D26), Fulcrum yields two records — nothing destroyed, dedup downstream in glue/Airtable — and two ADMINS editing one record merge silently. R-OFF-4's "collision surfaced, never merged" is met in spirit (no destruction) and failed in letter (no 409, no uniqueness).
- **R-OFF-7 (observability):** the device shows unsynced state; the org side has **no fleet-wide outbox/sync-failure feed.** Glue approximates it: nightly Query API job comparing `created_at` vs `system_created_at` lag per user, plus expected-vs-arrived check reconciliation ("operator says they submitted X" becomes a SQL query against Fulcrum's Query API). A phone silently failing to sync is found by *absence*, not by a tripwire. Weaker than CC-30 #206. Conceded.
- Session behavior on sign-out/member-removal with unsynced local records is **UNVERIFIED** — the offboarding one-pager must mandate force-sync before suspension, and this is a real hole for hostile churn.
- The A6 burden shrinks but doesn't vanish: the sync *engine* is vendor-verified at fleet scale; your **configuration** (data events, conditional requirements, defaults) still needs a per-platform smoke.

## 4. QR (R-QR-1)

Associate existing labels at record creation: barcode field, scan or type — native. Later resolution: **the mobile record search supports scanning a barcode to filter records** — scan → matching record from locally-synced data (offline-capable since search runs against the device DB) → open. What's missing is the ≤500ms **context-aware action sheet** (PRD §11.7: Available→Check Out; Checked Out→Check In/Report Issue; Vehicle→Start Daily Check): in Fulcrum the scan lands you on the record, and the *action* is a second act (open Custody Events, + , scan again or link). Custody-by-QR costs +2–3 taps per action vs AHITS's scan-to-action routing. Label-uniqueness 409 at association is not enforceable in-form; glue flags duplicates post-sync.

## 5. Auth & churn onboarding (R-AUTH-*) — the biggest field-facing concession

Every Fulcrum member requires an **email address**; onboarding is an emailed invitation (form or CSV bulk import: email, first, last, role). There is no PIN auth, no text-message copy-link invite, no regenerate-kills-the-old-link. All nine pilot operators do have personal gmail (charter §1) so it *works*, but for 20–90 churning semi-voluntary contractors: invite emails die in spam, password resets become a weekly support verb, and the D15/PR#200 machinery (onboard by text, email gates nothing) has no equivalent. SSO/SCIM exists on Elite but a corporate IdP for seasonal contractors makes this worse, not better. Mitigations that survive honesty: pre-create accounts during hiring paperwork with a staffer walking the password step; laminate a "reset your password" card. Session behavior is actually *better* than AHITS's: native app tokens persist (no synchronized mid-shift JWT cliff — R-AUTH-3 met by construction); revocation = remove the member (license frees for same-cycle reuse — good churn economics) — but see the unsynced-data caveat in §3. Account-action audit trail: Elite includes audit logging; record history shows who changed what per record version.

## 6. Automations & alerting (R-ALRT-1) — where the buy quietly becomes a build

Fulcrum **Workflows** trigger ONLY on record events — Created / Updated / Created-or-Updated / Deleted ("Triggers are currently limited to record events generated by the official web & mobile clients") — with actions Email (optional PDF attachment), Webhook, SMS, Assign Record; 10,000 runs/day. Everything event-shaped maps beautifully: failed check → email + SMS; damage report → assign + shop email with PDF work order; transfer created → SMS the recipient; HUB return logged → email the hub. **Everything absence- or time-shaped cannot fire**: missed-check-by-cutoff, maintenance overdue, equipment not returned, insurance expiry 30d/7d, inventory drift INV-1..5, stale-damage nag, PIN-locked equivalents. Those move to the **glue service**: a small Cloud Run cron reading the Query API (read-only SQL over all org data, 5,000 calls/hr, 10s query cap — ample at R-SCALE-1 volumes), holding activeKey-style dedup and auto-resolve state in its own small Postgres, dispatching via email/SMS. That is a rebuild of AHITS's alert engine minus the in-app bell (operators get SMS instead of bell + deep link — arguably *better* for this cohort, honestly a different product). The invariant checks (one open rig per vehicle, exact-restore on decline, reservation TTL release) live in the same service as post-hoc detectors + compensating writes, not preventions. **Name the shape plainly: the "buy" deletes the capture-layer build and relocates, does not delete, the systems build.**

## 7. Admin, reporting, maps, CC-18 (the rows this stack wins)

- **Fulcrum web**: per-app data viewers (filter/sort/search/map), record editor with full **Record History** (per-version diffs, restore — plan-gated "on certain plan types"), form builder, importer/exports, per-record PDF reports (30s render cap; PDF export covers first 10,000 records per run).

The corpus itself planned "Airtable sync for reporting/export" (PRD §9.3); this design just makes it load-bearing.

Admin map of checks/deployments with recency styling (recency bucket maintained as a glue-computed field), per-rig trail = map filtered to that rig's checks over time, crew map = shared app map of latest attestations; offline MBTiles basemaps on device; all positions remain attestation-derived — D2/D25 honored by configuration (no tracking feature is enabled).

## 8. External portal and the money loop — conceded, with the least-bad workarounds

- **R-PORT-1**: Data Shares are **public read-only URLs** (CSV/JSON/GeoJSON/KML), revocable only app-wide, no expiry, no per-record scoping, **no write-back**. ## Build estimate

Honest effort to reach the ACHIEVABLE subset of register MUSTs (i.e., excluding the conceded rows: PIN auth, Today view, DB invariants, enforced two-party transfer, tokenized portal, CC-17): **9–17 weeks of focused work, realistically one quarter.** Breakdown: (1) Fulcrum configuration — 11 apps, choice lists, per-vehicle-type template sections, data-events JavaScript (validation, computed status, nextDue math, duration stamping attempt), roles/app permissions/projects, offline MBTiles layers, per-record PDF report templates: **3–5 weeks** for someone fluent in Fulcrum + JS (Max would ramp in days, not weeks). (2) The glue service — webhook consumer, the cron alert engine re-hosted (missed-check-by-cutoff with business-date logic, overdue/expiry/drift detectors, activeKey-style dedup + auto-resolve state in its own Postgres, SMS/email dispatch), custody invariant detectors + compensating exact-restore writes, Hub Stock counter arithmetic, Airtable sync (webhook-driven upserts + nightly Query API reconciliation), lost-write reconciliation queries, Sentry: **4–8 weeks — this is CC-22 + CC-31-class work rebuilt against a SaaS API, with tests, and it is the part stakeholders will not see coming when they say 'buy.'** (3) Airtable base, views, interfaces, CC-18 timeline board: **1–2 weeks.** (4) Migration execution, onboarding/offboarding one-pagers, config-level device smokes (the A6 analog shrinks to a config pass), parallel-run support: **1–2 weeks.** WHO MAINTAINS IT: the same single person. The bus factor genuinely improves for the CAPTURE half — forms, choice lists, and workflows are legible to a successor admin in a way a bespoke Next.js/Prisma codebase is not, and the mobile client is vendor-maintained — but the glue service + data-events JS + Airtable formula layer is bespoke logic with the identical single-maintainer risk, now spread across three admin consoles and one codebase instead of one codebase. Net: the build does not disappear; roughly half of it is bought, the other half is relocated and miniaturized.

## Migration sketch

Mid-operation migration (rolling-start pilot live on CUL005, 9 operators, custody history that is the operation's evidence base): **Phase 0 (wk 0–1)** — stand up the Fulcrum org (Elite, 5-seat min), build the 11 apps against a seeded copy; import reference data via CSV importer (vehicles, serialized units with serial+QR values, items, hubs, member CSV) — importer caps at 10,000 records/run, ample; imported records do NOT fire workflows (documented), which is exactly what you want for backfill. **Phase 1 (wk 2–3), checks first** — dual-home the pilot cohort: operators install the native app and accept email invites (THE risky step — this is where churn-grade onboarding degrades from 'tap the text link, set a PIN' to 'find the invite email, create a password'; budget hands-on support per operator); cut the daily check over first (highest volume, Fulcrum's best lane); AHITS retains custody/transfers/requests/portal/alerts. Baseline the group text in the same window (the control arm the 07-28 review §6.1 says nobody captured). **Phase 2 (wk 4–6), custody on a weekend freeze** — freeze custody writes Friday evening; SQL-snapshot open state from Postgres (open rigs + kit, CHECKED_OUT units, reservation holds with TTLs, PENDING transfers/handoffs) → import; glue goes live (webhooks, crons, Airtable sync, invariant detectors); Monday operators run custody in Fulcrum. **Phase 3** — AHITS UI retired; **the AHITS Postgres is retained READ-ONLY as the 3-year evidence archive** (do NOT attempt to move ~57-migration-deep append-only history — CheckLog, AccountAuditLog, StatusLinkEvent, RequestLineEvent, idempotency keys — into a SaaS whose record history is plan-gated; R-DATA-2 is served by freezing, not migrating). Keep the Cloud Run service deployable-dark for one season: **rollback = re-point operators at AHITS**, whose schema was never touched — the rollback price is re-onboarding whiplash, not data. Named risks: (1) double-entry fatigue in the overlap week — keep it to ONE week per lane; (2) the cohort that just learned AHITS re-learns everything mid-season — adoption risk lands on the same ≥90% charter metric; (3) every migration week is a week not spent on CC-17, whose 6–10-week critical path D19 just committed; (4) StatusLink portal channels (WORK_ORDER/HUB_RETURN) have no landing zone — shops/hubs revert to email+phone on cutover day.

## Hybrid option

Strongest partial adoption: **Fulcrum as the capture lane over AHITS-as-system-of-record.** Daily checks + damage/problem reports + the incident log (NS-13, unbuilt in AHITS) move to Fulcrum native apps; a 1–2 week ingest adapter consumes Fulcrum webhooks and posts into AHITS's EXISTING idempotent routes (stamping businessDate from Fulcrum's client-side created_at, photos pulled from Fulcrum's API into Supabase Storage); AHITS keeps custody, transfers, requests, the tokenized portal, the alert engine, Today, and the whole CC-17 roadmap. WHAT IT BUYS: vendor-grade native offline for the single highest-volume, highest-risk flow — the exact layer where the 2026-07-28 review found five silent write-loss modes and where the full A6 matrix (D13's hard pre-CC-17 gate) has never run; the 28×5 device ceremony shrinks to a config smoke for the check lane; UXP-1's entire PWA defect class (update toast, hydration fossil, back-gesture wipe) exits the flagship flow; incident logging arrives free. WHAT IT COSTS: Fulcrum Elite for every operator ($8.6k/yr at 10 ops → $62.7k/yr at 90, peak-seat annual), the adapter build + its ongoing care, email-account onboarding for the churn cohort ON TOP of PIN onboarding, TWO apps and two identities on every phone (an R-FRIC-2 violation charged on every app switch), and Today's per-vehicle done/due chip degrading to sync-lag freshness. VERDICT, argued as the champion but honestly: as a LIVE stack it double-pays — CC-29 already closed the known holes, the pilot is live, and $55/u/mo to replicate a measured-35s flow while worsening R-FRIC-3 is only rational if (a) the full A6 matrix FAILS on iOS before CC-17 ships, or (b) the bus-factor event actually occurs. The rational purchase is the CONTINGENCY form: a 5-seat Elite sandbox ($3,300/yr) with the Daily Check app built, tested on both platforms, and documented as the break-glass capture path — cheap optionality against exactly the two tail risks AHITS cannot self-insure. A second, cheaper partial — Fulcrum only for admin-side ad-hoc inspections/evidence (5 seats, no operator exposure) — buys almost nothing the register values and is listed only for completeness.
