# AHITS — Field-Test Bug Diagnosis & Holistic Fix Proposals

_Prepared 2026-06-26 from the A6 device pass. Every root cause below is ground-truthed to specific code (file:line, quoted). Platform cells are marked **[observed]** (you saw it) or **[predicted]** (reasoned from code + known platform behavior — not device-tested)._

## Severity ranking

1. **G1 — End/return loses inventory (DATA LOSS).** Returned consumables can be credited to the cross-hub total but to **no hub**, making them vanish from every hub view; serialized units return with no hub; there is no rig-level destination selector. **Highest priority.**
2. **Offline auth drop (UR-007 / UR-026 / rental-offline).** Navigating offline logs the user out and they can't log back in offline — breaks the entire offline value proposition. **High.**
3. **UR-006 — "Launch Deployment" can't be activated.** Button silently disabled by gates whose controls live on a previous wizard step. **High (blocks core flow).**
4. **Rental add fails (operator) + G2 admin/operator parity inversion.** Operator's "Add Rental" hits an admin-only endpoint (403) with a swallowed error; admin actually *can* create rentals. **Medium-High.**

A single auth-gate change fixes both the rental-add failure and the G2 parity item, and a single auth/session change fixes the whole offline-logout cluster. So the four reported clusters collapse into **~4 focused PRs**.

## 1. G1 — End/return destination + "HQ" + disappearing items (DATA LOSS)

### Symptom
No way to pick one final destination for the whole rig; items appear to return to a non-existent "HQ"; some items disappear entirely after ending/returning.

### Root cause (verified)
- **No rig-level destination selector.** `DispositionDialog.tsx` has only an "Overall note" header (`:139-147`) and a **per-item, explicitly optional** hub dropdown that defaults to "— No specific hub —" (`:195-208`, default disp `{type:'HUB'}` with no `hubId` at `:71-94`). The quick-return path doesn't even take a hub.
- **The chosen hub is ignored for stock restore.** In every return path the restore hub is `drawnHubId ?? item.hubId`, **not** the hub the user picked:
  - per-item quick return `src/app/api/deployments/[id]/items/[kitItemId]/route.ts:117-124`
  - end deployment `src/app/api/deployments/[id]/end/route.ts:99-106`
  - bulk remove `src/app/api/deployments/[id]/items/route.ts` (same pattern)
- **The silent-loss bug.** When both `drawnHubId` and `item.hubId` are `null`, `restoreToHub(...)` is **skipped** but `inventoryItem.quantity` (the cross-hub total) is **still incremented**:
  ```ts
  // items/[kitItemId]/route.ts:117-124  (end/route.ts:99-106 identical)
  const hubForRestore = kitItem.drawnHubId ?? kitItem.item.hubId
  if (hubForRestore) { await restoreToHub(...) }      // ← skipped when null
  await tx.inventoryItem.update({ data: { quantity: { increment: restoreQty } } })  // ← always runs
  ```
  Result: the quantity exists in the grand total but in **no hub's `inventory_stock` row**, so it's invisible in hub-filtered views — "disappeared."
- **Serialized units return hub-less.** On return, units flip to `AVAILABLE` with **no hub written** (`end/route.ts:122-143`); the item's `hubId` updates only if `disp.hubId` was set (`:144-146`).
- **"HQ" is not in the code.** Repo-wide search for `HQ`/`Headquarters`/`Default Hub` = **zero matches**. "HQ" is the field user's label for items that came back with a `null`/blank hub. (It is generated by the null-hub paths above, not by a seed or default.)

> _Correction to an earlier note: the per-item return route is `[kitItemId]/route.ts` and **does** exist and handle the operator's "Return item"/"Log Usage" `DELETE`s (`my-rig/page.tsx:806, 827`). It is not a missing-route 404. The disappearance is the null-hub restore-skip above._

### Holistic fix
1. **`DispositionDialog.tsx`:** add a **required** rig-level "Final destination (hub)" selector at the top; seed every item's `disp.hubId` from it (overridable per item); remove the "— No specific hub —" option and the "(optional)" label; disable submit until every HUB-disposition item has a hub.
2. **Quick-return path:** add an optional `hubId` to the `[kitItemId]` DELETE body + a destination picker on the operator "Return item"/"Log Usage" dialogs (default = drawn/home hub).
3. **All three server routes:** make `hubId` **required** when `type === 'HUB'`; change restore hub to **`chosenHubId ?? drawnHubId ?? item.hubId`** and make `restoreToHub` unconditional whenever `restoreQty > 0` (with a required hub it can never be null → silent-loss path eliminated). Set `inventoryItem.hubId = chosenHub` on return; flip serialized units `AVAILABLE` and anchor them to that hub.
4. **One-off data cleanup:** backfill `inventory_items.hubId IS NULL` to a real hub and reconcile `inventory_stock` to per-hub sums (the `resyncItemTotal` primitive at `inventory-stock.ts:125-133` already exists) so existing phantom/"HQ" items reappear.

## 2. Offline auth drop — UR-007, UR-026, rental-offline logout

### Symptom
Offline, moving between tabs/pages signs the user out, and they can't log back in while offline. Coming back online silently re-authenticates and replays the queue (this part works).

### Root cause (verified — keystone)
The session is a stateless JWT cookie that is perfectly valid offline, but **the server re-validates it against the DB on every navigation and fails closed**:
- `src/app/(operator)/layout.tsx:11-12` (and `(admin)/layout.tsx`): `const session = await getSession(); if (!session) redirect('/login')`.
- `src/lib/auth/session.ts:61-72`: `getSession()` always does `prisma.user.findUnique(...)` and the `catch` returns `null` "if the DB is unreachable" — i.e. **offline = unauthenticated = redirect to /login** on any navigation that reaches the server.
Two reinforcing layers:
- `src/hooks/useAuth.ts`: SWR `fetcher` does `fetch('/api/auth/me').then(r=>r.json())`; offline it rejects → `error` set, `user` undefined, **no `keepPreviousData`, no persisted identity, no 401-vs-network distinction** → consumers see "logged out."
- `src/app/sw.ts`: `/api/auth/me` is **not** cached; the navigation cache matches only `/operator` (`startsWith('/operator')`), so **`/admin/*` browse navigations and un-precached routes hit the offline server** → the layout redirect above.

### Holistic fix (all layers — each platform fails through a different one)
1. **`session.ts`:** fail **open** on an *infra* error — on a caught DB/connection error, trust the already-verified JWT claims and return a session; fail **closed** only when the DB *successfully* reports `!isActive` / tokenVersion mismatch. (Also hardens against transient DB blips online.)
2. **`(operator)/layout.tsx` + `(admin)/layout.tsx`:** gate on a **JWT-verify-only** check (local `jwtVerify`, no Prisma) — a locally-valid token renders the shell offline; revocation still bites online via the API routes returning 401.
3. **`useAuth.ts`:** add `keepPreviousData: true`, persist last-known identity (localStorage) and hydrate SWR fallback from it; only treat an actual **401** as logged-out, never a network error; expose `isOffline`/`isStale` instead of conflating with `isError`.
4. **`sw.ts`:** add a runtime-cache rule for `/api/auth/me` (StaleWhileRevalidate); broaden the nav matcher to `/operator` **and** `/admin`; precache the missing operator routes (or rely on the broadened NetworkFirst nav cache).

## 3. UR-006 — "Launch Deployment" can't be activated (online & offline)

### Symptom
The Launch button can't be tapped; filling in the note doesn't help. Same online and offline.

### Root cause (verified)
The `onClick={launch}` and server route are fine; the **`disabled` predicate** is the bug (`my-rig/page.tsx:548`):
```jsx
disabled={!note.trim() || loading || hasUnselectedSerialized || (hasConsumableInKit && !sourceHubId)}
```
`hasUnselectedSerialized` (`:223-225`) and `sourceHubId` (`:194-196`, `:277`) are set by controls on **wizard step 2** (the unit picker `:446-491` and the hub selector `:507-520`). On **step 3** the user only sees the note box — so if a serialized item has no unit picked, or a consumable has no source hub, the Launch button stays grey **with no explanation** (nothing rendered at `:542-553`). It reproduces identically online/offline because it's pure client state — `launch()`/`mutate()` is never reached. No viewport/overflow defect; the button is reachable, just disabled.

### Holistic fix
- Render the actual blockers near the Launch button when disabled ("Select a unit for serialized items", "Select a source hub for consumables" — `launch()` already computes the hub message at `:281`, just surface it at render time).
- Better: block "Next" out of step 2 until units + hub are chosen, **or** keep Launch enabled and have `launch()` jump back to step 2 with the error (the 409 path already does this at `:311-322` — reuse for the pre-flight checks).
- Add visible helper text on the disabled button so the reason is never invisible.

## 4. Rental add (operator) + G2 admin/operator parity

### Symptom
Operator "Add Rental Vehicle" does nothing online ("page skips and stays in place"); offline it also logs them out. Separately, you reported admin can't create a rental "like operator."

### Root cause (verified — the premise is inverted)
- **`POST /api/vehicles` is admin-only:** `src/app/api/vehicles/route.ts:92` `await requireAdmin()` → **operator gets 403**. The operator's "Add Rental" posts there first (`my-rig/page.tsx:1388`), so it 403s every time and the rental is never created. The payload itself is valid (matches `createSchema`).
- **Swallowed error:** the operator onClick has a `try/finally` with **no `catch`**, and `await vRes.json()` at `:1393` is **not** guarded (unlike the second call at `:1402`). If the response isn't JSON (e.g. the offline auth redirect to an HTML login page), `.json()` throws, `finally` resets the spinner, and `setRentalError` is skipped → dialog re-renders unchanged = "skips and stays in place."
- **G2 is backwards:** an **admin passes** `requireAdmin`, so the admin rental flow actually **works** (`admin/deployments/page.tsx:542-574` is a clean mirror with the toggle + form). The likely reason you saw "admin can't": you were viewing `/admin/deployments` **as an operator** — operators are admitted read-only (`(admin)/layout.tsx:14-15`), and the "Add Vehicles" `MutationButton` returns `null` for non-admins (`ReadOnly.tsx:57`), so the control simply isn't there. Admin already has parity **plus** extras operators lack (secondary-operator management, force-reassign, richer remove dispositions).

### Holistic fix
- **`src/app/api/vehicles/route.ts:92`:** change `POST` to `requireAuth()` then scope it — a non-admin may create **only** `isRental === true` (their own rig's rental); non-rental fleet creation stays admin-only:
  ```ts
  const session = await requireAuth(); if (!session) return 401
  if (session.role !== 'ADMIN' && parsed.data.isRental !== true) return 403
  ```
  This fixes the operator rental-add **and** satisfies the G2 parity goal (both roles can add rentals; admin already could).
- **Fix error handling:** guard `:1393` with `.json().catch(() => ({}))` and add a `catch` that sets `rentalError`; consolidate the operator's inline handler into a named `handleAddRental` mirroring admin so the two can't drift.
- The offline-logout half of the rental symptom is fixed by the auth cluster (§2).

## Recommended fix sequencing (≈4 PRs)

1. **PR-1 (DATA LOSS): G1 end/return destination + null-hub restore + backfill.** Stop losing inventory first. (DispositionDialog + 3 routes + a small data backfill.)
2. **PR-2 (offline auth): the §2 keystone** — `session.ts` fail-open, layout JWT-only gate, `useAuth` keepPreviousData/persist, `sw.ts` caching. Unblocks UR-007/026 and the offline half of rental.
3. **PR-3 (rental + parity): `/api/vehicles` gate** to `requireAuth`+isRental scope, operator error-handling fix, named handler. Fixes rental-add and G2.
4. **PR-4 (UR-006): Launch button** blocker-surfacing / step-2 gating.

Each ships through the normal `development` → staging flow, with a focused re-test on the Android PWA (the platform that surfaced all four) plus a desktop control.

> **Security note (PR-2):** "fail open on infra error" is deliberate and scoped — it trusts a **cryptographically valid, unexpired** JWT when the DB is unreachable, and still honors revocation/suspension whenever the DB *is* reachable (including all API mutations). This is the standard offline-PWA posture, but it's a real tradeoff worth your explicit sign-off.
